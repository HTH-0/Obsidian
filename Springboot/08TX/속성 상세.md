### ✅ `@Transactional` 속성 상세 정리

```java
@Transactional(
    rollbackFor = SQLException.class,
    transactionManager = "transactionManager"
)
```

- `rollbackFor`: 기본적으로 `RuntimeException`과 `Error`만 롤백 대상. **체크 예외(Exception)**는 명시하지 않으면 커밋됨. 따라서 `SQLException.class`를 명시함.
    
- `transactionManager`: 프로젝트에 트랜잭션 매니저가 여러 개일 경우 **명확히 지정하지 않으면 충돌 또는 예외 발생** 가능. 이 설정은 필수.
    

---

### ✅ 트랜잭션 매니저 중복 시 주의사항

- `@Bean(name = "transactionManager")`는 **Spring의 기본 트랜잭션 매니저 명칭**이므로, JPA와 함께 쓸 때 충돌 가능.
    
- 따라서 **명칭 구분 필수**: `transactionManager` vs `jpaTransactionManager`
    
- 실제 운영 환경에서는 AOP 포인트컷 등을 이용해 트랜잭션 범위를 더 정교하게 제어하기도 함.
    

---

### ✅ 테스트 결과 확인 시 주의할 점

- 테스트 후 INSERT 쿼리가 날아간 것처럼 보일 수 있음 → 하지만 `SQLException`이 발생했기 때문에 실제로는 **롤백되어 DB에는 반영되지 않음**
    
- 이걸 확인하려면 테스트 후 DB 조회 시 데이터가 없음을 확인해야 함 → 트랜잭션이 제대로 작동했는지 검증하는 포인트
    

---

### ✅ 실무 적용 예시

- 예: 일부 서비스에서 **읽기 작업은 JPA**, **쓰기 작업은 배치로 JDBC 처리**하는 경우가 있음.
    
- 이럴 때 `@Transactional(transactionManager = "jpaTransactionManager")` 또는 `"transactionManager"`를 **상황에 따라 선택적으로 지정**함.
    

---

### ✅ EntityManagerFactory와의 연관성

```java
public JpaTransactionManager jpaTransactionManager(EntityManagerFactory emf)
```

- JPA 트랜잭션은 **EntityManagerFactory와 연동**되어야 정상 작동
    
- 따라서 Spring은 `JpaTransactionManager` 내부에서 `EntityManager`를 생성 및 관리함
    
- `dataSource2`도 같이 명시해줘야 **JPA + DataSource 기반 트랜잭션 연동**이 완료됨
    

---

### ✅ 왜 JPA와 JDBC 트랜잭션을 나눴을까?

- 실습 목적 외에도 실무에서 다음과 같은 이유로 나눌 수 있음:
    
    - **레거시 시스템**과의 통합: 기존 시스템은 JDBC, 신규는 JPA 기반
        
    - **성능 튜닝 목적**: JPA의 쓰기 지연(flush 타이밍)보다 JDBC가 예측 가능
        
    - **동일 서비스 내 이질적인 트랜잭션 요구**: 예를 들어 로그 저장은 JDBC, 주요 도메인은 JPA
        

---

## 📌 보완 요약

- `@Transactional`의 핵심 속성(`rollbackFor`, `transactionManager`)은 실무에서도 자주 튜닝 포인트가 됨
    
- 트랜잭션 매니저가 여러 개 존재하면 명확한 지정 필수
    
- 테스트의 성공 여부는 실제 DB 반영 여부로 판단
    
- 실무에서 JDBC/JPA를 병행할 수도 있어, **이중 트랜잭션 매니저 구조는 중요한 실전 패턴**
